# Код-ревью репозитория «Мир Гольфа»

Дата проверки: 21.11.2026. Проверены все 16 файлов в `main`.

## Итог

Прототип честный: данные не выдумываются, у каждого турнира есть ссылка на первоисточник,
монитор уважает `robots.txt` (fail-closed) и не извлекает победителей. Это сильная сторона.
Но проект **не запускается по своей же инструкции** и содержит несколько реальных багов.

---

## Критично

**1. Структура каталогов не совпадает с README.**
README велит `cd mobile` и `cd backend`, но в репозитории нет ни `mobile/`, ни `backend/`:
все файлы лежат в корне и названы как скачанные из чата — `App (1).js`, `main (1).py`,
`schema (1).sql`. Пробелы и скобки в именах ломают импорты и CI.

**2. Импорт в планировщике указывает в никуда.**
`scheduler (1).py` делает `from app.collectors.monitor import run_all`,
а файл называется `monitor (1).py` и лежит в корне. Планировщик упадёт на старте.

**3. Монитор не найдёт реестр источников.**
В `monitor (1).py`: `ROOT = Path(__file__).resolve().parents[3]`. Файл в корне репозитория,
значит `parents[3]` уходит выше корня, и `sources.json` не будет найден
(а имя файла вообще `sources (1).json`). Нужен явный путь или `parents[0]`.

**4. Один и тот же URL в реестре 6 раз.**
В `sources (1).json` записи `moscow_golf`, `spb_golf`, `mos_oblast_golf`, `krasnodar_golf`,
`krasnoyarsk_golf` указывают на один и тот же `rusgolf.ru/.../tournament-calendar`.
Монитор проверит одну страницу 6 раз, а при изменении создаст 6 записей в очереди проверки.
Нужна дедупликация по URL (проверять страницу один раз, привязывать к нескольким регионам).

**5. Три независимых копии реестра источников и они уже разошлись.**
`main (1).py` (14 записей), `sources (1).json` (13), `App (1).js` (14). В JSON нет
`mos-golf.ru`, `golf.mossport.ru`, `mofrg.ru`, `krasgolf.ru` — там регионы подменены
национальным календарём, а в API и в приложении эти сайты есть. Плюс разные схемы id:
`rusgolf-calendar` против `ru_golf_calendar`. Нужен один источник правды (JSON) и генерация
из него данных для API и клиента.

## Важно

**6. Статусы турниров устарели.**
В карточках «Предстоит» у турниров, которые уже закончились (2–9 и 5–8 ноября 2026).
Статус хранится строкой в данных, а не вычисляется из дат, и сравнивается по отображаемому
тексту: `EVENTS.filter(e => e.status === 'Предстоит')`. Нужен машинный статус
(`scheduled / live / finished / needs_review`) и вычисление из дат.

**7. Нет CORS в API.**
`main (1).py` без `CORSMiddleware` — веб-клиент (и HTML-версия) не сможет обращаться к API
из браузера.

**8. Нет ограничения размера ответа в мониторе.**
`response.text` читается целиком, лимит стоит только на обрезку текста после разбора.
Один тяжёлый ответ — и процесс съест память. Нужны `stream=True` и лимит байт.

**9. Проверка `robots.txt` только для исходного URL.**
После редиректа на другой домен правило уже не проверяется. Нужно проверять
`response.url` после запроса.

**10. Нет паузы между запросами и ретраев.**
13 источников проверяются подряд без задержки, при 429/503 нет backoff. Риск блокировки
по IP и «тихих» ошибок.

**11. Избранное не сохраняется.**
`useState([])` в `App (1).js` — после перезапуска список пуст. Нужен `AsyncStorage`.

**12. Детальный экран держит объект, а не id.**
`setSelected(event)` — при обновлении данных карточка покажет старое состояние.

**13. Ошибки открытия ссылки проглатываются.**
`Linking.openURL(url).catch(() => {})` — пользователь не узнает, что ссылка не открылась.

**14. README противоречат друг другу.**
Четыре файла README разной степени актуальности. Нужен один.

## Мелочи

- `from fastapi import HTTPException` внутри функции — импорт в теле, вынести наверх.
- `verified_at: Optional[str]` вместо `datetime` — теряется валидация.
- Нет `/tournaments/{id}`, `/results`, `/v1`-версии, хотя схема БД для них готова.
- В API 2 турнира, в приложении 3 — расхождение демо-данных.
- `status` в API латиницей, в UI по-русски — нет общего словаря.
- Фильтр `(filter === 'Гольф' && e.sport === 'Гольф') || ...` избыточен: `e.sport === filter`.
- Поиск не ищет по организатору, стране и датам, хотя данных для этого достаточно.
- Нет пустого состояния, когда фильтр ничего не нашёл.
- `__init__ (1).py` и `__init__ (2).py` — пустые файлы по 1 байту.
- Нет ни одного теста. Хотя бы парсер статусов и дедупликация источников тестируются легко.
- SQLite без WAL и индексов по `source_id` — на объёме вырастет время проверки.
- `connect()` вызывается на каждый источник — лишние открытия БД.

## Что сделано хорошо

- У каждого турнира есть `source` и текстовая заметка о том, что нужно перепроверить.
- Победитель не заполняется без протокола — это соблюдено и в данных, и в UI.
- `robots.txt` проверяется до запроса, при неудаче — запрет (fail closed).
- Честный `User-Agent` с местом для контакта администратора.
- Монитор сохраняет снимок, хеш и найденные ссылки — база для будущего разбора.
- Схема PostgreSQL продумана: `change_log`, `confidence`, `source_excerpt`, `verified_at`.

## Что я сделал в HTML-версии

Файл `index.html` в корне — то же приложение, но без Expo/React Native, одним файлом:

- вкладки «Турниры», «Аналитика», «Источники» с адресами `#/tournaments`, `#/analytics`,
  `#/sources` — работает кнопка «Назад» на телефоне;
- **статус турнира вычисляется из дат**, а расхождение с заявленным статусом показывается
  предупреждением (пункт 6);
- избранное сохраняется в `localStorage` (пункт 11);
- детальный экран открывается по id через адрес `#/event/<id>` (пункт 12);
- поиск ищет по названию, месту, организатору, уровню, виду спорта и датам;
- фильтры: вид спорта, регион, уровень, «только избранное», сортировка;
- «Аналитика» считает реальные числа по демо-данным: месяцы, регионы, виды спорта,
  доверие источников — вместо каркаса;
- реестр источников взят один раз из данных приложения, с поиском и фильтром по стране;
- пустые состояния, доступность (`aria-current`, `aria-pressed`, фокус), адаптив под телефон и десктоп;
- одна копия данных в начале файла — её легко заменить на `fetch('/tournaments')`, когда
  API будет с CORS.
